## 0. Wave 3 願景（一句話）

> **讓 Wave 2 的 StockDetail 從「需要記得 stockId 才能用」的工具，進化成「打開 App 就有事可做」的日常陪伴型產品。**

對應的核心轉變：
- **Wave 2**：使用者必須「主動輸入 2330」→ 才能看到資料
- **Wave 3**：使用者「打開首頁」→ 看見自選股即時報價、收到價格警示推播、用中文「台積」就能搜到 2330

---

## 1. 背景與目標

### 1.1 背景

Wave 2 已交付 StockDetail 完整骨幹（即時報價、K 線、基本面、籌碼），但目前存在三個阻擋使用者「持續回訪」的關鍵缺口：

1. **入口缺口**：使用者必須直接輸入 stockId（例如 `2330`），不符合一般散戶記得「台積電」而非代號的習慣
2. **記憶缺口**：每次重新查詢都要重新輸入；沒有「我關心的這 5-10 檔股票」的概念
3. **觸達缺口**：使用者必須主動打開網站才能知道「股價變化」，無法在「達到關注價位時被提醒」

對照 MVP PRD §2.1 的主要 Persona「陳大明」的使用情境（早盤通勤 / 盤中午休 / 盤後研究），目前的 v0.2.0 只滿足「盤後研究」的一部分；早盤與盤中的「快速看一眼」與「重大事件提醒」完全沒有對應功能。

此外，Wave 2 移交 1 項 P0 與 17 項 P1 技術債，其中 **Spring Security（OWASP A01）必須在 Wave 3 完成**，否則無法進入滲透測試與 prod 上線階段。

### 1.2 目標

在「不擴大新功能廣度」的前提下，把現有 StockDetail **變成日常工具**：

1. **降低進入門檻**：中文 / 英文 / 代號模糊搜尋，3 個字元內找到目標股票
2. **建立回訪鉤子**：自選股（Watchlist）讓使用者「有理由打開」首頁
3. **建立主動觸達**：價格警示讓系統「主動找使用者」，而非只能等使用者來
4. **完成 Wave 2 安全債**：Spring Security 上線、滲透測試完成，達到對外公測門檻
5. **每個功能都 release-able**：即使 Wave 3 中途中斷，已完成的功能也能獨立發布

### 1.3 成功指標（North Star Metrics）

| 指標 | Wave 2 基準值 | Wave 3 目標值（上線後 4 週） | 量測方式 |
|------|---------------|------------------------------|----------|
| 註冊使用者次月留存率（M1 Retention） | 待測（v0.2.0 上線後量） | ≥ 40% | Cohort 分析 |
| 平均每使用者每日 StockDetail 開啟次數 | 待測 | ≥ 3 次 | 行為日誌 |
| 設定自選股的使用者比率 | 0%（功能不存在） | ≥ 60%（註冊後 7 日內） | 後台統計 |

| 透過搜尋進入 StockDetail 的比率 | 0%（無搜尋功能） | ≥ 70%（vs 直接輸入網址） | 行為日誌 |
| API P95 延遲（含新功能） | < 200ms | < 250ms | APM 監控 |

### 3.1 In-Scope（Wave 3 必做）

- **F-W3-05：搜尋歷史紀錄（最近 10 筆）** — P1

### 3.2 Out-of-Scope（Wave 3 不做，明確排除）

| 項目 | 排除原因 | 預計 Wave |
|------|----------|-----------|
| ❌ 多個 Watchlist 群組（例如「短線」「長線」） | 增加複雜度且非首次使用者必要；先驗證單一群組行為 | Wave 4 |
| ❌ 技術指標疊加（KD/MACD/RSI/布林通道） | 工程量大（前端圖表 + 後端計算）；Wave 3 已含 P0 安全債 | Wave 4 |
| ❌ 個股新聞 / 公告聚合 | 需評估第三方授權與 MOPS 抓取穩定性，列為 Wave 4 探索 | Wave 4 |
| ❌ 產業 / 概念股分類 | 需建立分類資料表，資料來源待調研 | Wave 4 |
| ❌ 相對強弱比較（vs 加權指數 / 同產業） | 需先有產業分類；依賴上一項 | Wave 5 |
| ❌ 籌碼歷史趨勢圖（30/90 天） | Wave 2 籌碼僅有當日資料；需先擴充歷史資料表 | Wave 4 |
| ❌ 個股 buy/sell 明細擴充 | 列為 BUG-QUINCY-002，需評估 TWSE 替代來源 | Wave 4 |
| ❌ LINE Notify 推播 | LINE Notify 已於 2025/03/31 終止服務；改評估 LINE Messaging API | Wave 4（若採用） |
| ❌ 行動裝置 App（Native iOS/Android） | 暫以 PWA + Web Push 滿足行動需求 | v1.0 之後 |
| ❌ 收費機制 / 訂閱方案 | 先驗證 PMF（Product-Market Fit） | v1.0 之後 |

### 4.2 使用者故事（User Story）

#### F-W3-01：個股搜尋

##### US-W3-01-A：中文模糊搜尋

> **作為** 一位記得「台積電」但不記得代號 2330 的散戶，
> **我希望** 在搜尋框輸入「台積」就能看到「2330 台積電」的選項，
> **以便** 不需要 Google 查代號就能進入股票詳情頁。

**驗收條件（待 Peter 細化）**：
- 輸入 ≥ 1 字元即觸發搜尋（建議 debounce 250ms）
- 中文支援部分匹配（「台積」應命中「台積電」、「南亞科」搜「南亞」應命中「南亞」與「南亞科」）
- 英文 / 代號支援前綴匹配（「23」命中 `2301`、`2330`...）
- 結果列表顯示：代號、中文簡稱、所屬市場（上市/上櫃）
- 無結果時顯示「找不到符合的股票」（i18n）

##### US-W3-01-B：自動完成下拉

> **作為** 一位在手機上輸入較慢的使用者，
> **我希望** 看到下拉選單，可以用手指/鍵盤直接點選，
> **以便** 不需要打完整字串就能進入。

**驗收條件**：
- 結果最多顯示 10 筆
- 鍵盤上下鍵選擇 + Enter 進入
- 點選後直接導向 `/stocks/:stockId`

##### US-W3-01-C：熱門搜尋

> **作為** 一位剛打開首頁、還沒想好要看什麼的使用者，
> **我希望** 看到「現在大家都在搜什麼」，
> **以便** 獲得探索靈感。

**驗收條件**：
- 顯示前 10 名（依過去 24 小時搜尋次數，排除使用者自身）
- 熱門搜尋資料每小時更新
- **隱私要求**：熱門搜尋為彙總資料，不可暴露個別使用者搜尋紀錄

#### F-W3-02：自選股 Watchlist

##### US-W3-02-A：加入自選股

> **作為** 一位看完 StockDetail 的使用者，
> **我希望** 點一個按鈕就能把這檔加入我的自選股，
> **以便** 下次不用再搜尋。

**驗收條件**：
- StockDetail 頁面右上角加入「★ 加入自選股」按鈕
- 已在自選股的股票顯示「★ 已加入」（金色實心）
- 操作即時生效（樂觀更新 + 失敗回滾）
- **未登入使用者**：點擊按鈕跳出「請先登入」提示（不允許匿名收藏，待 Jamie 拍板 D2）

##### US-W3-02-B：首頁顯示自選股清單

> **作為** 一位早盤通勤的使用者，
> **我希望** 打開首頁就看到我 5-10 檔自選股的即時報價，
> **以便** 30 秒內掌握當日狀況。

**驗收條件**：
- 首頁取代目前的 placeholder
- 表格顯示：代號、名稱、現價、漲跌、漲跌幅、成交量
- 點任一列進入該股 StockDetail
- 空狀態（未加入任何自選股）：顯示引導 CTA「使用搜尋加入第一檔自選股」
- **效能**：10 檔自選股的彙整 API P95 < 500ms（避免 N+1）

##### US-W3-02-C：移除自選股

> **作為** 一位想清理列表的使用者，
> **我希望** 在自選股列表能直接移除股票，
> **以便** 不需要進入個股頁。

**驗收條件**：
- 列表每列右側有移除按鈕（垃圾桶圖示）
- 移除前彈出確認對話框（避免誤觸）
- 移除後即時更新列表

#### F-W3-03：價格警示 Price Alert

##### US-W3-03-A：設定突破價警示

> **作為** 一位希望在台積電跌破 580 元時收到提醒的使用者，
> **我希望** 在 StockDetail 設定「向下突破 580」警示，
> **以便** 不用一直盯盤。

**驗收條件**：
- StockDetail 頁面提供「設定警示」按鈕
- 警示類型：①向上突破指定價位 ②向下突破指定價位 ③日漲跌幅超過 X%
- 每個使用者每檔股票最多設定 5 條警示
- 警示觸發後自動標記為「已觸發」，不重複推播
- 使用者可在「我的警示」頁面管理（新增/啟用/停用/刪除）

##### US-W3-03-B：接收警示推播

> **作為** 設定了警示的使用者，
> **我希望** 警示觸發時能收到提醒，
> **以便** 即時做出反應。

**驗收條件（推播管道待 Jamie 拍板 D3）**：
- 觸發後 5 分鐘內送達
- 推播內容包含：股票名稱、觸發類型、當前價格、觸發時間
- 點擊推播可直接導向該股 StockDetail
- 使用者可關閉推播（Settings 頁）

##### US-W3-03-C：警示觸發判斷邏輯

> **作為** 系統，
> **我希望** 在每分鐘檢查一次價格警示，
> **以便** 在合理延遲內觸發。

**驗收條件**：
- 盤中（09:00-13:30 GMT+8）每分鐘檢查
- 盤後不檢查（節省資源）
- 假日不檢查（搭配 TD-7 交易日曆服務）

#### F-W3-04：Spring Security 上線 + 滲透測試（技術債清償）

> **作為** 平台營運方，
> **我們** 必須讓所有需要登入的 API 在未授權時回傳 401，
> **以便** 通過滲透測試並符合 OWASP A01 合規要求。

**驗收條件（細節由 Sophia/Brian 設計）**：
- 所有 `/api/v1/*` 端點（公開 API 除外）需 JWT 驗證
- 未授權請求回傳 HTTP 200 + `code: 3001`（依 API 設計規範 envelope）或 HTTP 401（待 Jamie 拍板 D4）
- 通過 OWASP ZAP 基線掃描（0 High / 0 Critical）
- 第三方滲透測試廠商簽核報告（待 Jamie 拍板 D5）

#### F-W3-05：搜尋歷史紀錄

##### US-W3-05-A：顯示最近搜尋

> **作為** 一位常查同樣幾檔股票的使用者，
> **我希望** 點開搜尋框就看到我最近搜過的 10 檔，
> **以便** 不用重複輸入。

**驗收條件**：
- 搜尋框 focus 但未輸入時顯示「最近搜尋」
- 顯示最多 10 筆，依時間降序
- 每筆右側有 X 可移除單筆
- 「清除全部」按鈕
- **儲存位置**：登入使用者存後端、未登入使用者存 localStorage（待 Jamie 拍板 D2）

### 5.2 Edge Cases

| 情境 | 預期行為 |
|------|----------|
| 搜尋無結果（例如輸入「abcdef」） | 顯示「找不到符合的股票」+ i18n + 引導去看熱門搜尋 |
| 自選股加入失敗（後端錯誤） | 樂觀更新後回滾、Toast 提示「加入失敗，請重試」 |
| 自選股已達上限（建議 50 檔） | 跳出提示「已達自選股上限，請先移除其他股票」 |
| 警示設定價位明顯不合理（如台積電設 1 元觸發） | 不阻擋（使用者自由），但 UI 提示「此價位距離當前 XX%」 |
| 警示觸發時使用者瀏覽器未開啟 | Web Push 進入作業系統通知中心；Email 進信箱 |
| 推播管道全部失敗 | 後台日誌記錄，不重試（避免延遲累積）；下次觸發再試 |
| 未登入使用者點「加入自選股」 | 跳出登入對話框 + 紀錄「登入後執行」意圖 |
| 滲透測試發現 High 漏洞 | 立即進入 Hotfix 流程（依 .claude/skills/hotfix-sop） |

## 6. 待 Jamie 拍板的關鍵決策

> 以下 5 個決策影響 SRS / 架構 / 工時，**請 Jamie 與使用者確認後再進入 SRS 階段**。

### D1：Wave 3 採「廣度」還是「深度」策略？

| 選項 | 說明 | 取捨 |
|------|------|------|
| **A. 廣度（推薦）** | 5 個 P0+P1 功能（搜尋 / 自選 / 警示 / Security / 搜尋歷史）+ Spring Security 上線 | 涵蓋日常使用核心鉤子；單一功能不一定深；4-6 週 |
| B. 深度 | 只做「搜尋 + 自選股 + Security」3 個功能，但加 8 個技術指標、籌碼歷史圖 | 體驗較完整；但少了「主動觸達」（警示），回訪率提升有限；4-5 週 |

> **Patricia 建議**：選 A。理由：警示推播是少數能讓使用者「離開 App 後還記得我們」的機制，價值 > 技術指標。技術指標可在 Wave 4 補強。

### D2：Watchlist 與搜尋歷史是否需要登入？

| 選項 | 自選股 | 搜尋歷史 | 取捨 |
|------|--------|----------|------|
| **A. 都需要登入（推薦）** | 後端儲存 | 後端儲存 | 跨裝置同步、可用於分析；門檻較高 |
| B. 都不需登入 | localStorage | localStorage | 門檻最低；換裝置就消失 |
| C. 混合 | 登入後端、未登入 localStorage | 同左 | 平衡，但 logic 複雜 |

> **Patricia 建議**：選 A。Wave 1 已有完整註冊登入流程，且 v0.2.0 註冊使用者轉換是核心指標；強迫登入有助於累積 MAU 數字（呼應 MVP PRD §1.3）。

### D3：價格警示推播管道選哪個？

| 選項 | 優點 | 缺點 | 工時 |
|------|------|------|------|
| **A. Web Push + Email（推薦）** | Web Push 即時、Email 落地保險；皆為標準協定 | Web Push 需 HTTPS + Service Worker；iOS Safari 16.4+ 才支援 | 5 day |
| B. Email only | 開發簡單、相容性最佳 | 即時性差（信箱檢查間隔不固定） | 2 day |
| C. LINE Messaging API | 台灣使用者習慣 | LINE Notify 已 EOL；改用 Messaging API 需申請官方帳號 + 訊息費用 | 8 day |
| D. 自建 PWA + Native Push | 完整體驗 | 工程量爆炸 | 20+ day |

> **Patricia 建議**：選 A。理由：①符合 v0.2.0「Web 為主」的策略 ②iOS 16.4+ 已涵蓋 80%+ 台灣 iPhone 使用者 ③避開 LINE Messaging API 的成本 ④Email 作為 fallback 確保不漏訊息。
>
> **若使用者堅持要 LINE 推播**：建議延至 Wave 4 並評估 Telegram Bot 作為替代（已有 TD-8 預留 chat_id 上傳 API）。

### D4：未授權請求回傳 HTTP 401 還是 HTTP 200 + code 3001？

| 選項 | 說明 | 取捨 |
|------|------|------|
| **A. HTTP 200 + code 3001（推薦）** | 完全符合現有 [API 設計規範](../../.claude/rules/api-design.md) Envelope Pattern | 一致性高；但滲透測試工具可能誤判「未保護」 |
| B. HTTP 401 | 符合 RFC 7235 標準；滲透測試不會誤判 | 違反現有 API 規範，需修改全前端攔截器 |
| C. 混合（401 含 envelope body） | 滿足兩邊 | 實作較複雜 |

> **Patricia 建議**：選 A，並在滲透測試報告附註說明此設計理由。或選 C 作為折衷，但需 Sophia/Brian 評估前端 axios 攔截器影響。
>
> **此決策需與 Sophia + Brian 共同確認**。

### D5：滲透測試廠商選定

> 此項屬於 Sophia 主導決策（已列在 Wave 2 收尾報告 §8）。Patricia 補充產品角度建議：
> - 建議選擇有「金融產業經驗」的廠商（理解台股應用情境）
> - 建議報告需含「未授權存取個資」「IDOR」「JWT 偽造」三項主檢
> - 預算建議：30-80 萬新台幣（中型 Web 應用基線）

## 8. 限制與假設

### 8.1 限制

- **股票主檔資料來源**：依賴 Wave 2 已建立的 `stock_info` 表；若主檔不全（特別是 OTC 股票），搜尋結果會缺失（呼應 TD-6 Wave 2）
- **Web Push 限制**：iOS Safari 需 16.4+；Android Chrome 需安裝為 PWA 後才支援背景推播
- **盤中資料延遲**：警示判斷依賴 v0.2.0 即時報價 API（已知有 cache TTL）；推播延遲 = cache TTL + 檢查間隔，無法低於 1 分鐘
- **滲透測試時程**：第三方廠商通常需 2-3 週前預約；建議 Wave 3 第 1 週就鎖定廠商
- **既有技術債連動**：TD-7（交易日曆服務）必須先完成，否則警示在週末/假日會誤觸發

### 8.2 假設

- 使用者已通過 Wave 1 註冊登入（無需新增註冊流程）
- 使用者瀏覽器允許推播（首次使用會詢問權限）
- TWSE / OTC 股票主檔在 Wave 3 開始前由 Bruno 確認資料完整度
- Wave 2 後端架構（M-QUOTE / M-FUND / M-CHIP）API 不需重大改動
